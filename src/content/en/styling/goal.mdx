## Why make "styling" its own part {#why}

When building LPs, you wrote CSS directly. You'll still write CSS in React, but **how you write and manage it** changes. The biggest headache is **class-name collisions**, which show up as a project grows.

- `A.css` has `.card`, and `B.css` also has `.card`. One overrides the other.
- "Which file is this `.title` style actually coming from?" becomes impossible to answer.

SCSS Modules solve this by **scoping styles to each component**. The `.card` you write in `ProductCard.module.scss` only applies inside `ProductCard`, and it will never clash with a `.card` in another file. This "collision-free peace of mind" is the foundation for writing styles in React.

## How this part is structured {#roadmap}

Working top to bottom, we'll build up SCSS Modules step by step.

1. **Why SCSS Modules** — actually trigger a global CSS collision and see it happen.
2. **Your first .module.scss** — `import styles` and apply it with `className={styles.card}`.
3. **SCSS features** — make styles easier to write with nesting, `&`, `$` variables, and `@mixin`.
4. **Design tokens and theming** — group colors into CSS variables (`--x`) and support light/dark.
5. **Responsive** — line things up nicely on phones too, with media queries and grid.
6. **Conditional classes** — switch classes based on stock and favorite state (clsx).
7. **Capstone** — actually finish off the list and the cards.

Each page has the **full code** and **practice**. Don't just read — write it yourself in `my-shop` and watch the screen change.
