## What's different between a direct import and fetch {#diff}

The `import products from './products.json'` you've used so far and the `fetch` you're about to use are fundamentally different.

| | direct import | fetch |
| --- | --- | --- |
| When it loads | bundled at **build time** | from the server at **runtime** |
| Speed | instant (it's right there) | takes time |
| Failure | never | yes (signal, server) |
| Updates | fixed until you rebuild | can always get the latest |

`import` is "data **baked into** the app," while `fetch` is "data you **go and get** each time."

## When to use fetch {#when}

You don't need to make everything a `fetch`. Here's a rough guide for choosing.

- **Leaving it as an import is fine** … small, fixed data (a list of categories, config values, and so on). If it doesn't change, baking it in is enough.
- **Use fetch** … data that lives on a server, data that gets updated, large data, and data that requires login.

A product list really comes from a server, so in this part we switch it to `fetch`.

## The subject matter for this part {#material}

Setting up a real API right away is a lot of work, so first we'll **`fetch` our own JSON file**. Put `products.json` in the `public/` folder and you can retrieve it at the URL `/products.json`.

```tsx
fetch('/products.json') // go and get public/products.json
```

What you do is the same as with a real API (communicate against a URL), so **in production you just swap out the URL**.

```tsx
fetch('https://api.example.com/products') // this is how it'd look for the real thing
```

## Our standard {#standard}

<Std
  decision="Import the file directly while the data is fixed and small. Move to fetch when the data can change without a rebuild"
  alt="Content that changes but is still owned by developers — a pricing table, a feature list — is often better served by a build-time import from a CMS export than by a runtime fetch. The question is who edits it and how often, not how big it is."
>

A direct import is resolved at build time, which makes it fast, type-checked and impossible to fail at runtime. Those are real advantages and worth keeping for as long as they hold. The moment the data has to change without you shipping a new build — stock, prices, anything a non-developer edits — the import stops being an option and everything on this page starts to apply.

</Std>

- Data that changes, is large, or lives on a server → `fetch`. Small, fixed data → `import` is enough
- The subject matter is `fetch('/products.json')` against `public/products.json`. For a real API you just swap out the URL
