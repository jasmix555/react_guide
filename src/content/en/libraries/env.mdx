## Why split config values into a file {#why}

**Config values** like a "site name" or an "API URL" end up scattered all over your code if you write them directly, and then you have to hunt them down when you want to change one. You also sometimes want different values in development and production (a test URL versus a production URL, for example).

So we gather these values in one place, a **`.env` (environment variables file)**, and read them from code by name. Vite has this mechanism built in from the start, so you don't need a library.

## Write in .env and read with VITE_ {#basic}

At the top of your project (the same place as `package.json`), create a file called `.env`. The contents are just "name=value," one per line.

```bash title=".env (new file)"
VITE_SHOP_NAME=Everyone's Products
```

From code, you read it by writing `import.meta.env` followed by the name.

```ts title="src/App.tsx"
const shopName = import.meta.env.VITE_SHOP_NAME
console.log(shopName) // Everyone's Products
```

<Callout type="warn">

Whenever you create or edit `.env`, **stop the dev server (`npm run dev`) once and start it again**. `.env` is read at startup, so editing it while the server is running won't take effect. This is the cause of most "the value won't change" problems.

</Callout>

## Break it on purpose: forget the VITE_ {#break-prefix}

This is the spec that trips people up the most. Vite **only passes names starting with `VITE_` to the screen (the browser-side code)**. As a test, let's put a name without the prefix.

```bash title=".env"
SHOP_NAME=Everyone's Products      # no VITE_ prefix
VITE_SHOP_NAME=Everyone's Products  # this one has it
```

```ts
console.log(import.meta.env.SHOP_NAME)      // undefined <- not passed
console.log(import.meta.env.VITE_SHOP_NAME) // Everyone's Products
```

`SHOP_NAME` is `undefined`. Because it doesn't start with `VITE_`, it's **deliberately not passed** to the browser side. This isn't a bug, it's a **safety spec** we'll explain next. When you get "I wrote it in `.env` but it's `undefined`," suspect a missing `VITE_` prefix first.

## Why only VITE_ — don't put secrets here {#security}

The answer to "why doesn't it just pass everything?" is the most important thing on this page. **Anyone can see the contents of code that reaches the browser.** That's because your JavaScript is downloaded to the user's PC and runs there.

In other words, a value you pass to the screen with `VITE_` is **the same as publishing it to the whole world**. That's why Vite is designed to "only pass what has `VITE_` = only pass what you've explicitly marked as OK to publish," preventing secrets from leaking by accident.

<Callout type="warn">

**Never put API secret keys, passwords, database connection info, and the like in `.env` with a `VITE_` prefix.** They become fully visible the moment they reach the screen. Secret information belongs on the server side, not in the browser (that's beyond the scope of this guide, so we'll learn it separately when you need it). The only things safe to put in `.env` are "values that don't matter if they're public."

</Callout>

## Don't commit .env {#gitignore}

Because `.env` holds per-environment values, the rule of thumb is **don't commit it to Git** (`create vite`'s `.gitignore` includes `.env` from the start). Instead, it's common to share a **`.env.example`** with empty values as a sample that shows "what names are needed."

```bash title=".env.example (values empty; this one you share)"
VITE_SHOP_NAME=
```

That way, other people can tell "ah, I need to set up `VITE_SHOP_NAME`," and each person writes the actual value in their own `.env`.

```bash title=".env"
VITE_MAX_ITEMS=8
MAX_ITEMS=8
```

```ts
console.log(import.meta.env.VITE_MAX_ITEMS) // '8' (VITE_ prefix means it's readable)
console.log(import.meta.env.MAX_ITEMS)      // undefined (no VITE_ means it isn't passed)
```

Only `VITE_MAX_ITEMS`, with the `VITE_` prefix, is passed to the screen; the plain `MAX_ITEMS` is `undefined`. By the way, the value you read is a string (`'8'`), so when you want to use it as a number, convert it with `Number(...)`. Don't forget to restart the dev server after editing `.env`.

</Together>

## Our standard {#standard}

<Std
  decision="Gather config values in .env, and add VITE_ only to the values used from the screen. Never put secret info there. Don't commit .env; share .env.example instead"
  alt="If there's just one value and it's a fixed value meant to be public anyway, it's fine to make it a constant in code rather than forcing it into .env. .env shines when you want to change values per environment, the count grows, or you want to share a sample."
>

The only things you put in `.env` are "values that don't matter if they're public." Assume anything with a `VITE_` prefix is visible to the whole world. Don't pass secret keys or passwords to the browser. `.env` is each person's own (don't commit it), and you share the names that are needed via `.env.example`.

</Std>

## When things go wrong {#trouble}

- **Wrote it in `.env` but it's `undefined`** ... Check that the name has a `VITE_` prefix, and that you restarted the dev server after saving `.env`.
- **The value is a string and awkward to work with** ... `import.meta.env.VITE_XXX` is always a string. Use `Number(...)` for numbers, and judge booleans yourself.
- **Accidentally committed `.env`** ... If it contained a secret, that value needs to be invalidated (regenerated). After that, check that `.gitignore` includes `.env`.
