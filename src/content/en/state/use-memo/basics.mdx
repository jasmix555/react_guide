## What useMemo actually is {#what}

**`useMemo` remembers the result of a calculation, and only redoes it when the inputs change.**

To see why that matters, you need one fact about React: when anything in a component updates, React **runs the entire component function again, top to bottom**. Not just the part that changed — all of it.

```tsx
// Bring in the useState tool from the React library.
import { useState } from 'react'

// Define a component. React calls this function again on EVERY update.
export function Shop() {
  // Hold a number that the screen shows. `count` reads it, `setCount` changes it.
  const [count, setCount] = useState(0)

  // ↓ This line runs again every single time `count` changes — even though
  //   sorting has nothing at all to do with the counter.
  const sorted = [...products].sort((a, b) => a.price - b.price)

  // Describe what the screen should look like right now.
  return (
    <div>
      {/* Show the number, and add one to it when the button is pressed. */}
      <button type="button" onClick={() => setCount(count + 1)}>
        {count}
      </button>
      {/* Show the first product from the sorted list. */}
      <p>{sorted[0].name}</p>
    </div>
  )
}
```

Press the button and the list gets sorted again, for nothing. With ten products that is invisible. With five thousand, every click stutters. `useMemo` is how you tell React: *keep the previous answer unless one of these inputs changed*.

<Callout type="analogy">

Think of a receipt taped to a drawer. Someone asks "how much is in here?" — you count it once and write the total on the receipt. Next time they ask, you read the receipt instead of recounting. You only recount when someone actually puts money in or takes it out. `useMemo` is the receipt; the dependency array is the list of things that count as "someone touched the drawer".

</Callout>

## The smallest working example {#minimal}

```tsx title="src/components/PriceList/PriceList.tsx"
// `useMemo` caches a value; `useState` holds a value the screen depends on.
import { useMemo, useState } from 'react'

// Describe the shape of one product, so TypeScript can check our code.
interface Product {
  id: number
  name: string
  price: number
}

// Describe what this component expects to be given from outside.
interface PriceListProps {
  products: Product[]
}

// Define the component. `{ products }` pulls the products list out of the props.
export function PriceList({ products }: PriceListProps) {
  // A counter that has nothing to do with the products. Changing it re-runs
  // this whole function, which is exactly the problem useMemo solves.
  const [clicks, setClicks] = useState(0)

  // Add up every price — but only when `products` actually changes.
  const total = useMemo(() => {
    // This function is the calculation. React runs it and keeps the result.
    return products.reduce((sum, product) => sum + product.price, 0)
  }, [products]) // ← the dependency array: redo the sum only if `products` changed

  return (
    <div>
      {/* Show the cached total, formatted with thousands separators. */}
      <p>Total: {total.toLocaleString()} yen</p>

      {/* Pressing this re-renders the component, but the sum is NOT redone. */}
      <button type="button" onClick={() => setClicks(clicks + 1)}>
        Clicked {clicks} times
      </button>
    </div>
  )
}
```

Three parts, exactly like `useEffect`:

```tsx
const total = useMemo(() => {
//    ↑              ↑
//    │              └─ ① the calculation. React runs it and keeps what it returns
//    │
//    └─ ③ the value that comes back — the cached result, not the function
  return products.reduce((sum, product) => sum + product.price, 0)
}, [products])
// ↑ ② the dependency array: if every value in here is unchanged since last render,
//     React skips step ① and hands you the previous result
```

## Scenario: filtering and sorting a product list {#filter}

The most common real use. A search box re-renders on every keystroke, and you do not want to re-sort five thousand rows because someone toggled an unrelated checkbox.

<Callout type="note">

**Try it first.** Build a product browser: a search box, an "in stock only" checkbox, and the matching products listed cheapest first. Aim for:

1. Both controls working, with the list updating as you type.
2. The filtering and sorting skipped entirely on any render where neither the products nor the two controls changed.
3. The original `products` array left untouched.

Hints: which values does the calculation actually read? Those, and only those, are the dependencies. `.sort()` rewrites the array it is given rather than returning a new one — what do you do before calling it? And should `query` itself be memoised, or is it something else?

</Callout>

```tsx title="src/components/ProductBrowser/ProductBrowser.tsx"
// useMemo caches the filtered list; useState holds the things the user changes.
import { useMemo, useState } from 'react'

// One product record.
interface Product {
  id: number
  name: string
  price: number
  inStock: boolean
}

// What this component receives from its parent.
interface ProductBrowserProps {
  products: Product[]
}

export function ProductBrowser({ products }: ProductBrowserProps) {
  // The text typed into the search box. Starts empty.
  const [query, setQuery] = useState('')

  // Whether the "in stock only" checkbox is ticked. Starts off.
  const [stockOnly, setStockOnly] = useState(false)

  // Build the list the user should see. This whole block is skipped on any
  // render where products, query and stockOnly are all unchanged.
  const visible = useMemo(() => {
    // Lower-case the query once, instead of once per product inside the loop.
    const needle = query.trim().toLowerCase()

    return products
      // Keep only products whose name contains the search text.
      .filter((product) => product.name.toLowerCase().includes(needle))
      // If the checkbox is on, also drop anything out of stock.
      .filter((product) => (stockOnly ? product.inStock : true))
      // Copy before sorting, because .sort() rewrites the array it is given.
      .slice()
      // Cheapest first.
      .sort((a, b) => a.price - b.price)
  }, [products, query, stockOnly]) // redo only when one of these three changes

  return (
    <div>
      {/* A controlled input: state holds the text, typing updates the state. */}
      <input
        type="search"
        value={query}
        onChange={(event) => setQuery(event.target.value)}
        placeholder="Search products"
      />

      {/* A controlled checkbox: `checked` reads state, clicking flips it. */}
      <label>
        <input
          type="checkbox"
          checked={stockOnly}
          onChange={() => setStockOnly((previous) => !previous)}
        />
        In stock only
      </label>

      {/* Turn each product in the cached list into a list item. */}
      <ul>
        {visible.map((product) => (
          <li key={product.id}>
            {product.name} — {product.price.toLocaleString()} yen
          </li>
        ))}
      </ul>
    </div>
  )
}
```

Line by line:

1. **`[products, query, stockOnly]`** — exactly the three values the calculation reads, and nothing else. Miss one and the list silently stops updating; add an extra and the cache stops hitting.
2. **`.slice()` before `.sort()`** — `sort` rewrites the array it is called on. `filter` already returned a new array here so it would technically be safe, but making the copy explicit means the line survives someone later removing the filters.
3. **`const needle` computed once**, above the loop, rather than calling `.toLowerCase()` on the query inside every single comparison.
4. **What is *not* memoised** is as deliberate as what is: `query` and `stockOnly` are plain state, and the JSX is rebuilt every render as usual. Only the one genuinely expensive step is cached.

## Scenario: a value you pass to a memoised child {#child-prop}

This is the case people miss, and it has nothing to do with the calculation being slow.

`memo()` wraps a component so it skips re-rendering when its props are unchanged. But it compares props with `Object.is`, and **a fresh array or object is never equal to the previous one** — even with identical contents. So an un-memoised array prop silently defeats the whole thing.

<Callout type="note">

**Try it first.** You have a `Dashboard` with a menu toggle and an expensive `Chart` child that receives an array of points built from a `sales` prop. Make opening the menu stop redrawing the chart. Aim for:

1. `Chart` wrapped so React can skip it.
2. Opening and closing the menu leaving the chart completely alone.

Hints: wrapping the child is necessary but not sufficient — try it and watch it keep redrawing. What exactly does the wrapper compare, and how does that comparison treat an array that the parent rebuilds in its own body every render?

</Callout>

```tsx title="src/components/Dashboard/Dashboard.tsx"
// `memo` wraps a component so it can skip re-rendering; useMemo keeps a value stable.
import { memo, useMemo, useState } from 'react'

// One row of chart data.
interface Point {
  label: string
  value: number
}

// A deliberately heavy child, wrapped in memo so it only redraws when needed.
const Chart = memo(function Chart({ points }: { points: Point[] }) {
  // Pretend this draws an expensive SVG. It should run as rarely as possible.
  return (
    <ul>
      {points.map((point) => (
        <li key={point.label}>
          {point.label}: {point.value}
        </li>
      ))}
    </ul>
  )
})

export function Dashboard({ sales }: { sales: number[] }) {
  // Unrelated UI state — opening a menu must not redraw the chart.
  const [menuOpen, setMenuOpen] = useState(false)

  // ✗ Without useMemo this array is rebuilt on every render, so `memo` sees a
  //    different prop every time and the Chart redraws even when nothing changed.
  // ○ With useMemo the SAME array object comes back, so memo's check passes.
  const points = useMemo(() => {
    // Turn each raw number into the shape the chart wants.
    return sales.map((value, index) => ({ label: `Day ${index + 1}`, value }))
  }, [sales]) // rebuild only when the raw sales data changes

  return (
    <div>
      {/* Toggling this re-renders Dashboard — but not Chart. */}
      <button type="button" onClick={() => setMenuOpen((previous) => !previous)}>
        {menuOpen ? 'Close menu' : 'Open menu'}
      </button>

      {/* The chart receives the same array object as last time, so it skips. */}
      <Chart points={points} />
    </div>
  )
}
```

Line by line:

1. **`memo(function Chart(...))`** — the wrapper. On its own it changes nothing here, which is the part that surprises people.
2. **`sales.map(...)` inside `useMemo`** — this is the line that makes the wrapper work. Written directly in the component body it produces a new array object on every render, `Object.is` says "different", and `memo` re-renders exactly as if it were not there.
3. **`[sales]`** — the raw data is the only input, so the derived array is rebuilt only when the data genuinely changes.
4. **The point here is identity, not speed.** `sales.map` is cheap; the memo exists so the *same array object* comes back, not to save the mapping work. This is the one case where you reach for `useMemo` without measuring first.

The function equivalent of this problem is [useCallback](/guide/state/use-callback/basics) — same reasoning, applied to functions instead of values.

## Scenario: a stable value for a dependency array {#deps}

`useEffect` compares its dependencies the same way `memo` compares props, so an object built during render re-triggers the effect forever.

<Callout type="note">

**Try it first.** A `Reveal` component takes a `threshold` prop and sets up an `IntersectionObserver` in an effect, passing an options object built from it. Write it so the observer is created once per threshold value rather than on every render. Aim for:

1. One observer per distinct `threshold`.
2. No endless teardown-and-rebuild.

Hints: what does an effect compare its dependencies with? What is `{ threshold }` on the second render compared with the first? And before you reach for a hook — there are two cheaper fixes here, and you should be able to name both.

</Callout>

```tsx title="src/components/Reveal/Reveal.tsx"
import type { ReactNode } from 'react'
// useEffect runs setup code; useMemo keeps the options object stable; useRef holds the node.
import { useEffect, useMemo, useRef, useState } from 'react'

interface RevealProps {
  children: ReactNode
  threshold: number
}

export function Reveal({ children, threshold }: RevealProps) {
  // A handle to the real DOM element, filled in by React after it renders.
  const boxRef = useRef<HTMLDivElement>(null)

  // Whether the element has scrolled into view yet.
  const [shown, setShown] = useState(false)

  // Build the observer's settings object ONCE per threshold value.
  // Written inline as `{ threshold }` it would be a new object every render,
  // so the effect below would tear down and rebuild the observer endlessly.
  const options = useMemo(() => ({ threshold, rootMargin: '0px' }), [threshold])

  useEffect(() => {
    // Copy the ref into a local variable so it cannot change under us.
    const element = boxRef.current

    // On the very first render the element does not exist yet — bail out.
    if (!element) return

    // Watch the element and report when it enters the viewport.
    const observer = new IntersectionObserver(([entry]) => {
      // Ignore the report if the element is still off screen.
      if (!entry.isIntersecting) return
      // Remember that it appeared, which redraws with the visible styles.
      setShown(true)
    }, options)

    // Start watching.
    observer.observe(element)

    // Stop watching when the component goes away or `options` changes.
    return () => observer.disconnect()
  }, [options]) // one stable object, so this runs once per threshold

  // `data-shown` lets CSS fade the box in without any JavaScript animation.
  return (
    <div ref={boxRef} data-shown={shown}>
      {children}
    </div>
  )
}
```

Line by line:

1. **`useMemo(() => ({ threshold, rootMargin: '0px' }), [threshold])`** — one object per threshold value instead of one per render. The extra parentheses around the object are required; without them JavaScript reads the `{` as a function body.
2. **`}, [options])` on the effect** — the effect now has a dependency that stays the same across renders, so it sets the observer up once and leaves it alone.
3. **`const element = boxRef.current` copied first** — the cleanup runs later, by which time the ref may already be `null`.
4. **`return () => observer.disconnect()`** — every observer you create needs a matching disconnect, or they accumulate across mounts.

<Callout type="warn">

Two cheaper fixes usually beat this one, which is why the brief asked you to name them. If the values are primitives, list them directly: `}, [threshold, rootMargin])` — no hook at all. If the object never changes, move it outside the component entirely, where it is created once for the whole app. Reach for `useMemo` only when the object genuinely depends on props or state.

</Callout>

## Scenario: an expensive format or parse {#format}

Building an `Intl` formatter is genuinely slow — hundreds of times slower than using one. Build it once.

<Callout type="note">

**Try it first.** Build a price tag that formats an `amount` as currency for a given `locale` and `currency`. Aim for:

1. The formatter constructed only when the locale or currency changes — not on every render, and not on every amount change.
2. Exactly one `useMemo` in the component.

Hints: there are two operations here — constructing the formatter and calling it. Only one of them is expensive. Which of the three props does the expensive one actually depend on?

</Callout>

```tsx title="src/components/PriceTag/PriceTag.tsx"
import { useMemo } from 'react'

interface PriceTagProps {
  amount: number
  locale: string
  currency: string
}

export function PriceTag({ amount, locale, currency }: PriceTagProps) {
  // Creating a NumberFormat is expensive; formatting with it is cheap.
  // Cache the formatter itself, keyed on the two things that define it.
  const formatter = useMemo(() => {
    return new Intl.NumberFormat(locale, { style: 'currency', currency })
  }, [locale, currency]) // rebuild only if the locale or currency changes

  // Using the cached formatter is fast, so this needs no memo of its own.
  return <p>{formatter.format(amount)}</p>
}
```

Line by line:

1. **`amount` is deliberately not a dependency.** The formatter does not depend on the number it will later format, so including it would rebuild the formatter on every price change — exactly the cost we are avoiding.
2. **`formatter.format(amount)` is left un-memoised.** Calling a formatter is cheap. A second `useMemo` around it would cost more in stored dependencies and comparisons than the call itself.
3. **The split is the whole technique**: find the expensive construction, cache that, and leave the cheap usage alone. The same shape applies to `Intl.DateTimeFormat`, `Intl.Collator`, and compiled regular expressions.

## Every way to call it {#signatures}

**The three dependency-array forms**, and only one of them is normally right.

```tsx
// ① Listed dependencies — the correct default. Redo only when one changes.
const total = useMemo(() => sum(items), [items])

// ② Empty array — compute once and keep forever. Only correct when the
//    calculation reads nothing from props or state.
const columns = useMemo(() => buildColumns(), [])

// ③ No array at all — recompute on every render. This is a useMemo that does
//    nothing except add overhead. Never write this.
const total = useMemo(() => sum(items))
```

**Always return the value.** A concise arrow body returns automatically; a block body needs an explicit `return`.

```tsx
// ○ Concise body: the object after => is returned.
const style = useMemo(() => ({ width }), [width])

// ○ Block body: you must write `return` yourself.
const style = useMemo(() => {
  return { width }
}, [width])

// ✗ Block body with no return: `style` is undefined.
const style = useMemo(() => {
  ;({ width })
}, [width])
```

**Wrapping an object literal needs parentheses.** Without them JavaScript reads the `{` as the start of a function body.

```tsx
const config = useMemo(() => ({ threshold: 0.2 }), []) // ○ parens around the object
const config = useMemo(() => { threshold: 0.2 }, []) // ✗ returns undefined
```

**Memoising a whole piece of JSX** is legal — JSX is just a value — and occasionally useful when you cannot wrap the child in `memo`.

```tsx
// Keep this subtree's element object stable across renders.
const header = useMemo(() => <ExpensiveHeader title={title} />, [title])

return <div>{header}</div>
```

**Deriving from another memo** is fine, and each layer is cached independently.

```tsx
// Filter first — redone only when the list or the search text changes.
const filtered = useMemo(() => items.filter((i) => i.name.includes(query)), [items, query])

// Then sort the already-filtered list — redone only when `filtered` changes.
const sorted = useMemo(() => [...filtered].sort(byPrice), [filtered])
```

**`useMemo` is a hint, not a promise.** React reserves the right to throw the cache away — for example to free memory. Your code must still be correct if the calculation runs on every render, which means the function must be pure: no `setState`, no network calls, no DOM writes.

## Break it on purpose: leave a value out of the deps {#break-deps}

This is the failure worth feeling, because unlike most `useMemo` mistakes it does not make things slow — **it makes them wrong**, silently.

```tsx title="deliberately wrong"
import { useMemo, useState } from 'react'

export function Broken({ items }: { items: Item[] }) {
  // The tax rate the user can change.
  const [taxRate, setTaxRate] = useState(1.1)

  const total = useMemo(() => {
    // This calculation reads BOTH items and taxRate…
    return items.reduce((sum, item) => sum + item.price, 0) * taxRate
  }, [items]) // …but only items is listed here

  return (
    <div>
      <p>Total: {Math.round(total)}</p>
      <button type="button" onClick={() => setTaxRate(1.2)}>
        Raise tax to 20%
      </button>
    </div>
  )
}
```

Click the button. The tax rate genuinely changes, the component genuinely re-renders — and **the total on screen does not move**.

Nothing is broken in a way you can see. React compared the dependency array, found `items` unchanged, and did exactly what you told it to: handed back the cached answer, computed with the old tax rate. The number on screen is now confidently wrong.

Add the missing dependency:

```tsx
}, [items, taxRate])
```

**Every value the calculation reads goes in the array — not the ones you think might change, all of them.** This is why `react-hooks/exhaustive-deps` is switched on in this project, and why silencing it with a disable comment is almost always the wrong move: the lint rule catches exactly this class of bug, which produces no error and no crash.

## Cheat sheet: the shapes you will actually write {#catalog}

```tsx
// Caching an expensive calculation
const total = useMemo(() => items.reduce((s, i) => s + i.price, 0), [items])
const visible = useMemo(() => items.filter(matches).sort(byPrice), [items, query])

// Returning an object literal — note the parentheses
const style = useMemo(() => ({ width, height }), [width, height])

// Caching an expensive instance, not the result of using it
const formatter = useMemo(() => new Intl.NumberFormat(locale), [locale])

// A stable array or object prop for a memo() child
const points = useMemo(() => raw.map(toPoint), [raw])
<Chart points={points} />

// A stable object for a dependency array
const options = useMemo(() => ({ threshold }), [threshold])
useEffect(() => observe(options), [options])

// Chaining — each layer caches independently
const filtered = useMemo(() => items.filter(matches), [items, query])
const sorted = useMemo(() => [...filtered].sort(byPrice), [filtered])

// ✗ Not worth it — the memo costs more than the work
const count = useMemo(() => items.length, [items])

// ○ Just compute it
const count = items.length
```

## When to use it — and when not to {#when}

Use `useMemo` when one of these is true:

- The calculation is measurably slow — sorting, filtering or transforming thousands of items, parsing, building an `Intl` formatter.
- The result is an **object or array** passed to a `memo()` child, or listed in a dependency array. Here the point is stable identity, not speed, and it is worth doing without measuring.

Do not use it for these:

- **Cheap calculations.** `items.length`, `price * 1.1`, `` `${first} ${last}` `` — the memo costs more than the work. Just compute it during render.
- **Values you could keep in state instead.** If it is genuinely derived, derive it; if it is genuinely independent, use [useState](/guide/state/use-state/basics). `useMemo` is neither a store nor a substitute for either.
- **Functions.** A function is a value, so `useMemo(() => fn, deps)` works — but [useCallback](/guide/state/use-callback/basics) exists for exactly that and reads better.
- **Anything with a side effect.** Fetching, subscribing, writing to `document` — that is [useEffect](/guide/state/use-effect/basics). A memo may be discarded or re-run at React's discretion.
- **Values that must survive without triggering renders.** That is [useRef](/guide/state/use-ref/basics).

## Common mistakes {#mistakes}

**Leaving a value out of the dependency array.** This is the bug that produces wrong numbers rather than slow ones.

```tsx
// ✗ `taxRate` is missing, so the total keeps the tax rate from the first render
const total = useMemo(() => {
  // Add up the prices, then apply tax.
  return items.reduce((sum, item) => sum + item.price, 0) * taxRate
}, [items]) // ← taxRate is read above but not listed here
```

Change the tax rate and the number on screen does not move, because React sees `items` unchanged and hands back the cached answer. Every value the calculation reads must be listed.

<Diff
  bad="useMemo(() => total(items) * taxRate, [items])"
  good="useMemo(() => total(items) * taxRate, [items, taxRate])"
  note="Anything the calculation reads goes in the array. A missing dependency freezes the result at its first value."
/>

**Putting a fresh object in the dependency array.** The cache can then never hit.

```tsx
// ✗ `options` is a new object every render, so the memo recomputes every render
const options = { currency: 'JPY' }
const label = useMemo(() => format(amount, options), [amount, options])

// ○ list the primitive the calculation actually depends on
const label = useMemo(() => format(amount, { currency }), [amount, currency])
```

**Memoising something trivial.**

<Diff
  bad="const count = useMemo(() => items.length, [items])"
  good="const count = items.length"
  note="Reading .length is far cheaper than storing dependencies and comparing an array every render."
/>

**Forgetting `return` in a block body.** The value becomes `undefined`, usually crashing a few lines later with "cannot read properties of undefined".

**Calling a hook inside the calculation.**

```tsx
// ✗ Error: hooks can only be called at the top level of a component
const value = useMemo(() => {
  const [x] = useState(0)
  return x
}, [])
```

Hooks are matched by call order across renders, and the memo's function does not run on every render. Move the hook out to the component body.

**Expecting `useMemo` to stop a re-render.** It does not. The component still re-renders; only the calculation inside is skipped. Stopping a *child* from re-rendering is `memo()`, covered on the [useCallback page](/guide/state/use-callback/basics).

Every `useMemo` costs something: React stores the previous dependencies and result, and compares the array on every render. For a cheap calculation that overhead is larger than the work you skipped. ## What React is doing under the hood {#internals}

`useMemo` stores two things in this component instance's hook slot: **the dependency array from the last render**, and **the value the function returned**.

On every render:

1. React builds your new dependency array — that part always runs, even when the memo hits.
2. It compares the new array against the stored one, **position by position, using `Object.is`**. Same length, same order, every slot equal.
3. All equal → React returns the stored value and **never calls your function**.
4. Any difference → React calls your function, stores the new result and the new array, and returns the new result.

Two consequences worth internalising. The comparison is **shallow**: `[{ id: 1 }]` and `[{ id: 1 }]` are two different objects and therefore not equal, which is the root of nearly every "my memo never hits" report. And the cache holds **exactly one entry** — it remembers the last result, not a history. Alternating between two dependency values means a miss every single time.

<Deeper title="Is useMemo guaranteed to keep the value?">

No, and the React documentation is explicit about it: `useMemo` is a performance hint. React may discard cached values — to free memory for offscreen content, for example — and recompute on the next render.

The practical rule this creates: **never store something in `useMemo` that would be wrong to recreate.** If losing the value would break your app — a WebSocket connection, an ID that must stay stable, a mutable instance other code holds — it belongs in [useRef](/guide/state/use-ref/basics) or state, not in a memo.

</Deeper>

## TypeScript notes {#typescript}

`useMemo` infers its type from what the function returns, so an explicit type argument is almost never needed.

```tsx
// TypeScript works out that `total` is a number.
const total = useMemo(() => items.reduce((sum, item) => sum + item.price, 0), [items])

// And that `names` is string[].
const names = useMemo(() => items.map((item) => item.name), [items])
```

**When inference is not enough**, it is the same situation as `useState` — an empty collection, or a union you want to keep narrow:

```tsx
// ✗ inferred as never[], so nothing can ever be pushed into it
const rows = useMemo(() => [], [])

// ○ say what it holds
const rows = useMemo<Product[]>(() => [], [])
```

**An object literal needs the wrapping parentheses**, or TypeScript reports a puzzling error because it is parsing a labelled statement, not an object:

```tsx
// ✗ error, and the message will not mention the missing parentheses
const style = useMemo(() => { width: 100 }, [])

// ○
const style = useMemo(() => ({ width: 100 }), [])
```

**Typing a memoised formatter or instance** is worth doing explicitly, so the return type is obvious to the next reader:

```tsx
// The type argument documents what comes out without opening the function.
const formatter = useMemo<Intl.NumberFormat>(() => {
  return new Intl.NumberFormat('ja-JP', { style: 'currency', currency: 'JPY' })
}, [])
```

**The dependency array is typed as `unknown[]`**, so TypeScript will not catch a missing dependency. That job belongs to the `react-hooks/exhaustive-deps` lint rule, which this project has switched on — do not disable it to silence a warning; fix the array or restructure the code.

## When things go wrong {#trouble}

- **The number on screen stops updating** … A value the calculation reads is missing from the dependency array, so you keep getting the cached answer — see [break it on purpose](#break-deps).
- **The memo never seems to hit** … Something in the array is a fresh object or array each render. React compares with `Object.is`; list the primitive fields instead.
- **`Cannot read properties of undefined`** … A block-bodied memo with no `return`. `useMemo(() => { … })` must return the value.
- **An error mentioning a label or an unexpected token** … An object literal without wrapping parentheses. `useMemo(() => ({ … }), [])`.
- **The child still re-renders even though I memoised its prop** … The child is not wrapped in `memo()`. Both halves are required.
- **The component still re-renders** … It always will. `useMemo` skips the calculation, not the render.
- **It got slower after I added memos everywhere** … Each memo stores an array and compares it on every render. Remove the ones around cheap calculations.
- **`react-hooks/exhaustive-deps` is warning and I want it quiet** … It is right. Add the dependency, or move the value into the calculation. A disable comment here is how the frozen-value bug above ships.
