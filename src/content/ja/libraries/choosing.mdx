## 一番良いライブラリは「入れないライブラリ」 {#why}

ライブラリは便利ですが、入れた瞬間から**あなたの管理対象**になります。更新が止まって古くなる、他の部品と相性が悪い、いつの間にか不具合が入る——面倒を見続ける相手が 1 つ増える、ということです。

だから選び方の一歩目は、逆説的ですが「**入れずに済ませられないか**」です。次の順で考えます。

1. **ブラウザや JavaScript の標準機能で足りないか？**（日付・配列・文字列などは標準が充実しています）
2. **すでに入っている部品で足りないか？**（同じことができる部品を二重に入れない）
3. それでも要るなら、**選ぶ**

上の 2 つで止まれば、それが一番ラクな正解です。

<Callout type="analogy">

道具箱と同じです。便利そうな工具を見かけるたびに買っていたら、箱はすぐパンパンになり、どこに何があるか分からなくなります。「今ある工具で無理か」を一度考えてから買うと、箱がすっきり保てます。

</Callout>

## まず標準で足りないか確かめる {#native-first}

「ライブラリを入れよう」と思ったとき、その多くは標準機能で足ります。例をいくつか挙げます。

- **日付を整える** → `new Date().toLocaleDateString('ja-JP')` で「2026/8/3」が出ます。専用ライブラリは、複雑な計算が要るまで不要。
- **配列を加工する** → `map` / `filter` / `find`（Part 2 でやりました）で大半は足ります。
- **クラス名を組み立てる** → これは標準だと少し面倒なので、`clsx` という小さな部品を使います（次のページ）。

「標準でどう書くんだろう」を **30 秒調べる**だけで、ライブラリを 1 つ減らせることはよくあります。

<Together
  task="「価格 1280 を『1,280円』のように 3 桁区切りで表示したい」。ライブラリを入れる前に、JavaScript の標準機能でできないか調べて書いてみてください。（ヒント：数値には toLocaleString というメソッドがあります）"
  hint="(1280).toLocaleString() で '1,280' になります。末尾に '円' を足せば完成です。"
>

```js
const price = 1280
console.log(price.toLocaleString() + '円') // 1,280円
```

3 桁区切りは、標準の `toLocaleString()` だけでできます。**専用のライブラリは要りません**。「これ、標準で行けるな」と気づけると、依存を 1 つ増やさずに済みます。まず標準を疑う——この癖が効いてきます。

</Together>

## 入れると決めたら、ここを見る {#criteria}

標準でも既存でも無理で、入れると決めた。そのときは、候補を **4 つの観点**で見比べます。すべて npm の各ライブラリのページ（`npmjs.com`）で確認できます。

- **メンテされているか** … 最終公開日（Last publish）が数年前で止まっていないか。放置された部品は避けます。
- **使われているか** … 週間ダウンロード数（Weekly Downloads）。多いほど、情報も多く、不具合も見つかりやすい。
- **型定義があるか** … TypeScript で使うので、型が付いているか（次のページで詳しくやります）。
- **大きすぎないか** … サイズ（Unpacked Size）や、それ自体が抱える依存の数。小さいほど安心です。

<Callout type="note">

npm のページを開くと、右側に「Weekly Downloads」「Unpacked Size」「Last publish」が並んでいます。左に「TypeScript」バッジや `types` の記載があれば型定義付きです。**この 3〜4 か所を見るだけ**で、ある程度の判断ができます。GitHub の Star 数や、最近の Issue のやり取りも参考になります。

</Callout>

## 迷ったら「小さく・枯れた」ものを選ぶ {#prefer-small}

同じことができる候補が複数あるときは、**小さくて・枯れている（長く使われて安定している）**ものを選びます。多機能で新しいものは魅力的ですが、学ぶことも、壊れる余地も増えます。

うちのスタックで選んでいる部品（`clsx`、`sass`、`react-router`、`motion`）は、いずれも**用途がはっきりしていて、広く使われているもの**です。「なんとなく人気だから」ではなく、「この作業のために、これを使う」と言える状態を保ちます。

## うちの標準 {#standard}

<Std
  decision="依存を足す前に必ず「標準／既存で無理か」を一度考える。入れるものはメンテ状況・利用数・型・サイズを確認した、用途の明確なものに限る"
  alt="社内で既に使っている部品があるなら、同じ用途の別ライブラリを新規に入れず、それに合わせます。統一されているほうが学習コストも管理コストも下がります。"
>

一番ラクなのは「入れない」こと。標準機能と、すでにある部品でまず考えます。入れると決めたら、放置されていないか・広く使われているか・型が付いているか・大きすぎないかを確認します。「なぜこれを入れたか」を一言で言える部品だけを、棚に並べます。

</Std>
